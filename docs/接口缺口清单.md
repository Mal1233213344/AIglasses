# 儿童 AI 英语眼镜项目接口缺口清单

## 1. 结论

当前需求文档已经足够做产品开发排期，但还不够支撑研发、测试、硬件三方直接并行开工。

最缺的是这些内容：

- 硬件协议细节
- 后端接口字段
- 数据模型定义
- 异常码和状态机
- 联调顺序

如果这些内容不先补齐，项目最容易出现的问题就是：

- APP 页面做完了，实际连不上设备
- 后端接口写完了，字段和硬件上报格式对不上
- Pro/Max 功能逻辑反复返工
- OTA、图传、照片同步在最后一周集中暴雷

## 2. 开发前必须冻结的协议

### 2.1 设备身份与型号规则

必须明确：

1. 设备唯一 ID 用什么字段表示
2. MAC 地址是否作为主标识
3. 标准版 / Pro 版 / Max 版的型号编码
4. 蓝牙广播名规则
5. 固件版本号格式
6. 设备是否支持序列号

建议产出：

- `device-identity-spec.md`

### 2.2 BLE GATT 协议

必须明确：

1. Service UUID 列表
2. Characteristic UUID 列表
3. 每个特征的读写/通知能力
4. MTU 大小
5. 指令包格式
6. ACK 机制
7. 超时与重试策略
8. 重连触发条件
9. 连接态状态机

建议产出：

- `ble-gatt-spec.md`

### 2.3 设备管控指令协议

文档里已经定义了功能，但没有定义协议字段。

必须明确：

1. 锁屏/解锁指令格式
2. 音量设置与最大音量锁定字段
3. 单次时长/每日时长字段
4. 功能开关字段
5. 远程关机/重启字段
6. 护眼提醒配置字段
7. 省电模式字段
8. 电量校准指令
9. 错误码

建议产出：

- `device-command-protocol.md`

### 2.4 离线指令机制

文档要求“设备离线时发送的远程指令，联网后自动执行，24 小时有效”，这里至少要补齐：

1. 指令 ID
2. 指令过期时间
3. 是否允许覆盖旧指令
4. 多条同类指令的优先级
5. 服务端缓存还是 APP 本地缓存
6. 执行结果如何回执

建议产出：

- `offline-command-spec.md`

### 2.5 OTA 升级协议

必须明确：

1. 固件包命名规则
2. 固件版本比较规则
3. 升级包清单结构
4. SHA256 校验字段
5. 升级前电量校验流程
6. 升级进度回传格式
7. 回滚触发条件
8. 灰度升级字段
9. 强制升级/可选升级策略

建议产出：

- `ota-spec.md`
- `ota-manifest-schema.json`

### 2.6 学习数据同步协议

必须明确：

1. 学习时长如何计算
2. 识别单词记录结构
3. 跟读练习结构
4. 拍照记录结构
5. 对讲呼叫记录结构
6. 数据批量上报格式
7. 增量同步游标
8. 去重规则
9. 离线缓存时长

建议产出：

- `learning-sync-spec.md`

### 2.7 照片同步协议

文档写了“WiFi 自动同步、增量同步、128KB 分片、断点续传”，但还缺：

1. 眼镜热点发现方式
2. 热点 SSID 命名规则
3. 密码下发方式
4. 照片列表接口
5. 单张照片元数据字段
6. 分片编号规则
7. 断点续传 token
8. 同步完成确认机制
9. 删除照片是删 APP 端、设备端还是双删

建议产出：

- `photo-sync-spec.md`

### 2.8 实时图传协议

这是最高风险模块之一，当前文档只给了目标指标，没有给协议。

必须明确：

1. 图像编码格式
2. 分辨率与帧率切换策略
3. UDP 端口
4. 首帧拉起流程
5. 丢包处理策略
6. 关键帧机制
7. 横竖屏与画面方向
8. 图传启动/停止握手
9. 眼镜热点连接成功后的发现流程

建议产出：

- `live-stream-spec.md`

### 2.9 语音对讲协议

必须明确：

1. 对讲建链流程
2. 呼叫方/接听方状态
3. OPUS 包封装格式
4. 上下行通道定义
5. 最大时长限制实现方式
6. 录音缓存规则
7. 断线重连策略
8. 回听录音存储策略
9. 噪声环境下的降噪策略是否由固件负责

建议产出：

- `voice-intercom-spec.md`

### 2.10 内容同步协议

必须明确：

1. 词库包格式
2. 音频包格式
3. 版本号规则
4. 按型号分发逻辑
5. 自动更新策略
6. 内容回滚机制
7. 缓存占用上限
8. 断点续传实现方式

建议产出：

- `content-sync-spec.md`

## 3. 后端接口还缺什么

建议在开工前补一版 OpenAPI，至少覆盖这些接口：

1. 验证码发送、登录、注销、协议确认
2. 设备绑定、解绑、设备列表、当前设备切换
3. 设备状态查询
4. 设备指令下发与执行结果查询
5. 学习数据上报与查询
6. 学习报告生成
7. 内容版本查询、下载地址获取、推送记录
8. 固件版本查询、升级任务创建、升级进度查询
9. 用户反馈、日志上传
10. 孩子信息管理
11. 推送 token 注册
12. 后台登录、权限、审计日志、报表导出

建议产出：

- `backend-openapi.yaml`

## 5. 哪些模块可以先开工

即使协议还没全出来，下面这些模块也可以先做：

1. 登录页与协议弹窗
2. 权限申请流程
3. 首页骨架和版本差异 UI
4. 个人中心
5. 后台权限管理 UI
6. 内容管理后台 UI
7. 数据模型与数据库设计

## 6. 哪些模块不建议盲做

下面这些模块如果没有协议，就不要急着写死：

1. BLE 连接流程
2. 设备指令发送
3. OTA 升级
4. 照片同步
5. 语音对讲
6. 实时图传
7. 离线指令补发

## 7. 最推荐的联调顺序

正确联调顺序建议如下：

1. BLE 扫描与绑定
2. 设备状态读取
3. 基础控制指令
4. 学习数据同步
5. 内容同步
6. OTA 升级
7. 照片同步
8. 语音对讲
9. 实时图传

这个顺序的原因是：

- 前 6 项决定主链路是否成立
- 最后 3 项是复杂网络能力，应该在主链路稳定后独立压测

## 8. 我对项目当前状态的判断

如果你现在就准备组队开发，我建议把“启动会”的目标定义成下面 3 项：

1. 确定移动端、后端、后台技术栈
2. 在 2 天内补齐设备协议文档
3. 在 3 天内冻结 OpenAPI 和数据库设计

只要这 3 件事完成，项目就能真正进入高效率开发阶段。
